# F16.1 — RTL8723BE complete hardware mapping baseline

Status: **reference-derived implementation baseline; not yet claimed boot-functional**.

This document defines F16.1 from the Linux RTL8723BE implementation as a hardware contract. It replaces register-by-register trial-and-error with a complete dependency model.

## Reference

Primary reference: Linux `drivers/net/wireless/realtek/rtlwifi/rtl8723be/`.
Relevant components include `hw.c`, `trx.c`, `trx.h`, `fw.c`, `fw.h`, `pwrseq.c`, `pwrseq.h`, `sw.c`, `phy.c`, `rf.c`, `reg.h`, and the common PCI/DMA layer.

The Linux source explicitly exposes 40-byte TX descriptors and 32-byte RX descriptors, including OWN, queue, MAC-ID, packet length, buffer address and status fields. The Linux hardware-init path also performs PCIe DMA-hang detection/reset, MAC initialization, firmware download, PHY MAC/BB/RF configuration, hardware configuration, RX-DMA release and PCIe DMA release.

## Target hardware

- PCI vendor: Realtek `0x10ec`
- PCI device: `0xb723`
- subsystem observed on HP TPN-W121: `103c:81c1`
- firmware: `rtl8723befw_36.bin`
- target OS: NetBSD 11 amd64

```text
PCI discovery
  -> PCI command / bus mastering
  -> MMIO BAR mapping
  -> PCIe ASPM / interface state
  -> card power sequence: CARDDIS -> CARDEMU -> ACT
  -> PCIe DMA hang check
  -> PCIe DMA reset if required
  -> MAC reset/initialization
  -> firmware download
  -> firmware ready
  -> MAC/BB/RF configuration
  -> DMA ring memory
  -> TX/RX descriptor rings
  -> RQPN/LLT/queue configuration
  -> RX/TX DMA enable
  -> interrupt masks and handler

```

The exact ordering is a hardware dependency, not a NetBSD API preference.

## PCI/MMIO mapping

Linux accesses RTL registers through its PCI/MMIO abstraction. NetBSD must use `bus_space` after the PCI BAR has been mapped. Register offsets remain hardware constants.

Important reference registers observed in the Linux RTL8723BE path include:

- `0x003`: `SYS_FUNC_EN + 1`, PCIe DMA reset/enable bit
- `0x005`: `APSD_CTRL`
- `0x006`: power-sequence status/polling
- `0x058`: `REG_SYS_ISO_CTRL`
- `0x05a`: clock/power control
- `0x062`, `0x063`: clock/power control
- `0x068`, `0x069`: generation/cut-dependent power control
- `0x075`: PCIe power sequence control
- `0x0e4`: PCIe MIO interface
- `0x0e8`: PCIe MIO interrupt/data path
- `0x0ec`: HPON FSM
- `0x0f0`: SYS_CFG
- `0x0f8`: MAC/PHY control
- `0x0fc`: SYS_CFG1
- `0x100`: CR, MAC TX/RX function control
- `0x284`: RX DMA control
- `0x301`: PCIe DMA control
- `0x350`: PCIe DMA debug/diagnostic path

The exact symbolic names and bit masks must be taken from the Linux register definitions rather than reconstructed from observed values.

## DMA model

### TX

Linux defines a 40-byte TX descriptor. Important fields include:

- DWORD 0: packet size, offset, BMC, HTC, first/last segment, OWN
- DWORD 1: MAC-ID, queue select, rate ID, security type, packet offset
- DWORD 2/3: aggregation, RTS/CTS, sequencing and rate-control flags
- DWORD 4/5: TX rate, fallback, bandwidth and short-GI controls
- DWORD 7: TX buffer size
- DWORD 8/9: hardware sequence controls
- DWORD 10: TX buffer DMA address
- DWORD 12: next descriptor address

NetBSD implementation must preserve little-endian descriptor layout and ownership semantics exactly.

TX lifecycle:

```text
mbuf
 -> bus_dmamap_load_mbuf()
 -> descriptor population
 -> bus_dmamap_sync(PREWRITE)
 -> OWN=1
 -> TX polling/doorbell
 -> hardware DMA
 -> completion/OWN=0
 -> bus_dmamap_sync(POSTWRITE)
 -> unload/free
```

### RX

Linux defines a 32-byte RX descriptor. Important fields include:

- DWORD 0: packet length, CRC32, ICV, driver-info size, shift, PHY status, SWDEC, OWN
- DWORD 1: MAC-ID and aggregation status
- DWORD 2/3: report and receive-rate status
- DWORD 4/5: bandwidth, SPLCP and timestamp information
- DWORD 6: RX buffer DMA address

RX lifecycle:

```text
DMA buffer allocation
 -> bus_dmamap_load()
 -> descriptor buffer address
 -> EOR on final descriptor
 -> OWN=1
 -> RX DMA
 -> IRQ/status
 -> OWN=0
 -> bus_dmamap_sync(POSTREAD)
 -> packet extraction
 -> replacement/rearm
 -> OWN=1
```

## IRQ model

Interrupt handling is not simply an enable bit. The Linux driver exposes explicit `enable_interrupt` and `disable_interrupt` operations and a hardware IRQ vector/status model.

NetBSD must preserve:

```text
PCI interrupt establishment
 -> read interrupt status
 -> mask/classify source
 -> ACK/clear source
 -> process RX/TX/firmware/error work
 -> DMA synchronization
 -> re-arm/unmask
```

No interrupt source should be enabled before its associated DMA/ring state is valid.

## Firmware model

Firmware is part of the hardware protocol.

```text
NetBSD firmware loader
 -> RTL8723BE firmware download
 -> MCU/FW ready handshake
 -> H2C mailbox/command path
 -> firmware C2H/event path
 -> operational state
```

`rtl8723befw_36.bin` must be validated before download and the firmware-ready state must be observed before dependent MAC/PHY operations.

## Power/reset model

Linux `rtl8723be_hw_init()` explicitly checks for PCIe DMA hangs, resets the PCIe DMA interface when required, powers off an already-active adapter, initializes MAC, downloads firmware, configures PHY, then releases RX and PCIe DMA.

The Linux PCIe DMA reset sequence includes:

1. unlock system-register writes
2. pause RX/TRX DMA
3. pause PCIe DMA
4. reset MAC TRX when applicable
5. reset PCIe DMA
6. re-enable PCIe DMA
7. restore PCIe autoload state
8. release DMA only at the correct phase
9. restore register lock

This ordering must be preserved on NetBSD.

## API mapping

| Linux | NetBSD | Hardware meaning |
|---|---|---|
| PCI/MMIO access | `bus_space_*` | same register protocol |
| coherent DMA allocation | `bus_dmamem_*` | same DMA memory |
| `dma_map_*` | `bus_dmamap_*` | same physical DMA mapping |
| `dma_sync_*` | `bus_dmamap_sync` | same CPU/device ownership transition |
| Linux IRQ registration | NetBSD PCI interrupt APIs | same hardware interrupt |
| `request_firmware` | NetBSD firmware framework | same firmware image |
| `skb` | `mbuf` | packet buffer only |
| Linux 802.11 | NetBSD IEEE80211 | protocol framework only |

## F16.1 implementation rule

F16.1 must not introduce a new hardware state based on guesswork. Every MMIO write, DMA transition, descriptor field, IRQ source and firmware command must be traceable to the reference implementation or to a required NetBSD API adaptation.

The known-good F15.1 kernel remains the recovery anchor and must not be overwritten.
